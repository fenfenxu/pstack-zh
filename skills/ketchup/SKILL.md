# Ketchup

用直白的话，把后面发生的事补给用户。补的是这次对话里，用户写下 `/ketchup` 之前自己写的最后一条消息之后的一切。通知，以及子代理的结果，都不算用户的消息。用 [`/bro`](../bro/SKILL.md) 的直白口气来写，跳过它把上一条消息再说一遍的那一步。就当用户只记得自己的上一条消息，后面的事都不记得。PR、分支或 agent，一律用用户认得的名字，不要用你干活时自己编的叫法。

## 收集变化

这一轮保持只读。收齐那条消息之后你自己做的事、子代理的报告，以及这次对话里其他人发的消息。核对这次对话涉及的每个 PR、每条 CI 运行、每个 agent 现在的状态。说清哪些还在跑，哪些你没能核对。

待用户处理的事，是只有用户能做的决定或步骤，例如产品上的选择、批准、不可逆的操作，或你没有的访问权限。还在等用户的，也算，哪怕是在用户上一条消息之前提出的。你自己还能做的工作，不算。

## 写下回复

开头用一句话说明有几件待用户处理的事，或者一件都没有。如果什么都没发生，也没有事在等用户，就这样说，然后停。

然后说发生了什么，最重要的放前面。每条结果都写上，并写明它对用户意味着什么。跳过什么都没变的步骤。你自己还能做的剩余工作，用一行写明。

然后给每件待用户处理的事一份简短摘要，带上够做决定的背景。写清要做的决定、为什么现在要紧、有哪些选项、每个选项的代价、你的建议，以及用户不回复会怎样。某一部分不知道，就说不知道，不要猜。有细节就附上链接。摘要要让用户不打开链接也能做决定。
