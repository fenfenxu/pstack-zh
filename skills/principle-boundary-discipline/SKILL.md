# 边界纪律

将验证、类型收窄和错误处理放在系统边界。无条件信任内部代码。业务逻辑放在纯函数中。外壳层应薄而机械。

**原因：** 分散的验证既嘈杂又冗余，还会制造虚假的安全感。把逻辑从框架接线中剥离，才能在不依赖框架的情况下测试。

**模式：**
- **在边界处**（CLI 参数、配置文件、外部 API、网络协议）：验证、返回错误、防御性处理。
- **系统内部：** 类型化数据、错误传播、不重复验证。信任类型。
- **跨越边界。** 暴露领域概念，而非边界的私有表示。通用机制留在内部，专用策略放在边缘。

**应用：**

验证与错误处理：
- 在解析时验证配置（边界处），而非业务逻辑内部
- 在边界将原始数据解析为领域类型
- 不要通过公共面向重新导出传输、存储、框架或 wire 类型
- 若边界已验证，调用链深处不要冗余 nil 检查

代码组织：
- 业务逻辑放在无框架依赖的纯函数中
- 解析函数：从原始字节到类型化状态的纯变换
- 提示词构建：结构化状态进，字符串出
- 评分与评估：从状态到结果的纯变换

**检验：**
- 「这些数据此刻是否正在跨越系统边界？」若不是，验证就是冗余的。
- 「这能否做成纯函数，由外壳层直接调用？」若能，就提取出来。
