# Notes 验证地图

这个目录是验证 Notes 面向用户行为时持续维护的依据。操作应用之前先读这份索引，再把对应的功能文件当作操作步骤来用。

## 基础前提

- 在 `http://127.0.0.1:4173` 启动 Notes，用一个用完即弃的数据目录。
- 设置 `NOTES_DATA_DIR=/tmp/notes-verify-$RUN_ID`，让同时进行的几次运行不共享状态。
- 预先放入标题为 `Quarterly plan` 和 `Grocery list` 的笔记。
- 把 `control-notes` 和 `notes` CLI 加进 `PATH`。
- 运行 `control-notes doctor`，要求 URL、数据目录和构建版本都符合预期。
- 不是这次验证运行启动的实例，绝不去操作。

## 操作约定

- 每份步骤都从基础状态开始，除非它的前提另有说明。
- 优先用 ARIA 角色和无障碍名称，不用 CSS 选择器或 DOM 位置。
- 每条命令都照字面执行。引号里的名称和参数原样保留。
- 浏览器操作通过 `control-notes browser` 来跑。
- 终端操作通过 `control-notes cli -- <command>` 来跑。
- 改动数据之后，把预置数据恢复原样。清理时不要删掉证明材料。

## 证明和跳过的报告方式

- 记录用户的操作和操作后的状态，不只是最后一屏。
- UI 的证明包括一份 ARIA 快照，和一张能看出是哪个应用的截图。
- CLI 的证明包括命令、stdout、stderr 和退出码。
- 改动数据的证明要包括从另一个只读视图再看一次存下来的值。
- 每份证明材料都记下功能 ID 和用了哪个入口。
- 走不通的路径，报告尝试过的命令和没满足的前提。
- 跳过的入口不要说成已经通过另一条路径验证过。

## 每个功能文件怎么写

每个功能文件以一个一级标题开头，接一段话描述用户能看到的行为。之后按下面的顺序，正好用四个二级标题。

1. `Sub-features` 列出简短的 ID，每个行为一行。
2. `How to get to it (user POV)` 列出用户的每一个入口。
3. `Driving it with <harness>` 以 `Preconditions:` 开头，用带标签的列表项，把每个用户操作和确切的命令、可观察的结果配成一对。
4. `Gotchas` 列出会浪费一次验证运行或让它作废的陷阱。

地图里不写实现细节。只写用户路径、稳定的抓手、需要的状态、命令和可观察的证明。

## 功能

- [创建笔记](./create-note.md) 覆盖在浏览器和 CLI 里创建、取消、持久保存和清理。
- [搜索笔记](./search.md) 覆盖从工具栏、键盘和 CLI 搜索，以及有匹配、无结果和清空这几种状态。
