# 体验优先

当实现便利与用户 delight 冲突时，选择 delight。

- 每个功能、控件和选项都必须有理由
- 少做、做好（三个功能的 polished 体验胜过十个功能的粗糙体验）
- 承诺前先原型（设计决策在可丢弃 HTML 中比生产代码更便宜）
- 把细节做对（过渡、对齐、间距、反馈、错误状态）
- 收紧核心循环（每个功能应服务 central workflow，否则让开）

用户是会用到这份工作的人。做 UI 时，用户是最终用户。做库或内部 API 时，用户是 import 它的同事。以后维护这段代码的工程师也是用户。把他们的体验放在同一架天平上，并且从他们的角度说明影响。

基础应服务体验。Foundational thinking 治理工作的*顺序*。本原则治理*目标*。
